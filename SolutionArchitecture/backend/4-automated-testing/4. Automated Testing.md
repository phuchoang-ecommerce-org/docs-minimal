# 4. Automated Testing

Required workflow from [roadmap section 4](inkdrop://note/uUXxpSnh), revision 87, and [Adjust Content - 2](inkdrop://note/Pso19weS), revision 14, read through MCP on 2026-11-07. This file contains reusable scenario and test templates for future implementation. It does not report backend tests as executed. Existing [BA use cases](../../../BusinessAnalyst/use-cases.md) and [business rules](../../../BusinessAnalyst/business-rules.md) define behavior; unresolved policies remain unresolved.

## Mandatory test-first gate

For every feature or behavior-changing fix: fill the scenario template, write automated tests, observe the expected failing behavior, then implement the function and make those tests pass. Tests are not a final phase delegated after implementation. A test can expose an existing regression without introducing another production change first.

| Gate | Required artifact | Exit condition |
| --- | --- | --- |
| Scenario | Filled template with UC/BR, boundary/failure cases, architecture rules and expected observations | No guessed product policy; unresolved dependent scenario marked BLOCKED |
| Test code | Automated test source, fixtures, deterministic clock/IDs and execution command | Tests exist before feature implementation; API/type shells may be introduced only to compile tests |
| RED | Failing test evidence and its cause, tied to source revision | Failure proves missing/wrong behavior, not dependency download, syntax error, unavailable DB or disabled test |
| GREEN | Minimal feature implementation and rerun | Relevant behavior, architecture, mapping and persistence checks pass |
| Refactor | Updated implementation with unchanged expectations | Same checks pass; no skipped/assertion-weakened test to hide a defect |
| Handoff | Scenario-to-test map and actual results | PASS/FAIL/BLOCKED/NOT RUN are explicit; no claim of runtime proof from document validation |

An environment failure blocks the dependent RED gate; prepare scenario/test code and continue independent tasks, but do not declare test-first complete or implement the dependent function anyway. Bootstrap may create build configuration, interfaces and test doubles needed to execute tests; it must not implement business behavior before its tests. Existing behavior that already passes gets a regression test and evidence; do not manufacture a failure by damaging correct code.

## Scenario template

Copy one block per independently observable behavior into the implementation task's test specification. Replace every angle-bracket field before coding the behavior. Store the specification under the implementation repository's agreed test-spec folder and link it in the task/PR.

```yaml
scenario_id: AT-UC-<number>-<case>
title: <observable behavior>
source_revision: <docs commit or content hash; note revision if used>
trace:
  use_cases: [<UC-ID>]
  business_rules: [<BR-ID>]
  architecture_rules: [<ARCH-ID or none with reason>]
level: <domain | application | mapper | mvc | postgres | architecture | profile>
actor: <Guest/Member/Seller/Admin and owned/foreign resource relation>
preconditions: [<state, ownership, payment state, fixtures>]
input: <valid values, boundary values or invalid request>
given: <deterministic setup>
when: <one command/query or synchronized competing actions>
then:
  returned_result_or_error: <exact value/code/status>
  persisted_state: <changed and unchanged rows/state>
  forbidden_effects: <no foreign write, no extra decrement/audit success, no secret leak>
fixtures: <builder/factory, fixed clock, generated IDs, database isolation>
concurrency: <barrier, independent transactions, timeout, allowed outcomes or not applicable>
automation:
  test_class: <package.Class>
  test_method: <method or parameterized cases>
  command: <actual project command>
red_evidence: <revision, command, failure assertion and observed cause>
green_evidence: <revision, command, result/report path>
cleanup: <rollback/truncate allowed test tables/drop disposable DB; do not delete audit history>
status: <DRAFT | READY | RED | GREEN | BLOCKED | NOT_RUN>
open_decisions: [<decision and owner; empty when none>]
```

## Filled scenario example


## Technology roles and test suites

| Technology | Project use | Boundary |
| --- | --- | --- |
| JUnit 5 / Jupiter | Unit and parameterized scenarios, lifecycle, tags | Use Java 21 and a compatible pinned Jupiter 5 engine; do not silently upgrade to JUnit 6 |
| Mockito + Mockito JUnit Jupiter | External collaborator stubs/verification for application tests | Do not mock the aggregate under test or simulate SQL locking with a mock |
| AssertJ | Values, exception/state assertions, collections | Assert stable behavior and invariants, not incidental internal call order |
| Spring Boot Test | MVC slices, full context, real transaction/security wiring | Unit/mapping tests do not start the whole app |
| ArchUnit + Modulith verification | Code direction, cycles, internal boundaries and CQRS | Does not prove authorization, SQL atomicity or source-retained Lombok usage |
| PostgreSQL test database | Flyway/JDBC/constraint/concurrency checks | Use isolated real PostgreSQL (existing Compose setup or approved Testcontainers); never H2 for locking claims |

Use `testImplementation` for JUnit Jupiter API/params, Mockito Jupiter, AssertJ, Spring Boot Test and `archunit-junit5`; runtime Jupiter engine/platform launcher must match. The selected Boot test BOM may carry a different JUnit major; inspect resolved dependencies and pin a compatible matrix before accepting bootstrap. Keep test libraries out of production runtime. Register `integrationTest` explicitly and make `check` depend on it. Tag or isolate unit, MVC, architecture and PostgreSQL suites; fail CI if an expected suite discovers zero tests.

JUnit's [guide](https://docs.junit.org/5.13.4/user-guide/index.html), [Mockito API](https://javadoc.io/doc/org.mockito/mockito-core) and [AssertJ guide](https://assertj.github.io/doc/) describe the test mechanisms. [Spring Boot Test](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html) provides context/slice support; choose imports and starters for the pinned Boot release rather than copying mismatched version examples.

## Domain, application and mapping templates

Project types and fixtures below are intended implementation contracts, not classes present in this documentation repository.

```java
@org.junit.jupiter.params.ParameterizedTest
@org.junit.jupiter.params.provider.ValueSource(ints = {0, 6, -1})
void rejectsInvalidRating(int stars) {
  org.assertj.core.api.Assertions.assertThatThrownBy(() -> new Rating(stars))
      .isInstanceOf(IllegalArgumentException.class);
}

@org.junit.jupiter.api.Test
void cancellationCannotRestoreStockAfterAnyPortionWasPaid() {
  var order = OrderFixtures.placedWithTwoPendingPortions(); // real aggregate
  order.recordCod(order.firstPortionId(), order.firstSellerId(), FIXED_TIME);
  org.assertj.core.api.Assertions.assertThatThrownBy(order::cancel)
      .isInstanceOf(IllegalOrderTransition.class);
  org.assertj.core.api.Assertions.assertThat(order.isCancelled()).isFalse();
}
```

```java
@org.junit.jupiter.api.extension.ExtendWith(org.mockito.junit.jupiter.MockitoExtension.class)
class RecordCodPaymentTest {
  @org.mockito.Mock OrderRepository orders;
  @org.mockito.Mock AuditAppender audit;
  @org.mockito.Mock SellerDirectory sellers;
  RecordCodPaymentHandler handler;

  @org.junit.jupiter.api.BeforeEach
  void setUp() {
    handler = new RecordCodPaymentHandler(orders, audit, sellers, FIXED_CLOCK);
  }

  @org.junit.jupiter.api.Test
  void foreignSellerCannotSaveOrAuditPayment() {
    var order = OrderFixtures.pendingFor(SELLER_B);
    org.mockito.Mockito.when(sellers.requireSellerIdForAccount(ACCOUNT_A)).thenReturn(SELLER_A);
    org.mockito.Mockito.when(orders.findParentId(PORTION_B)).thenReturn(order.id());
    org.mockito.Mockito.when(orders.lockById(order.id())).thenReturn(order);
    org.assertj.core.api.Assertions.assertThatThrownBy(
        () -> handler.execute(new RecordCodPayment(PORTION_B), Actor.seller(ACCOUNT_A)))
        .isInstanceOf(NotFound.class);
    org.mockito.Mockito.verify(orders, org.mockito.Mockito.never()).save(org.mockito.ArgumentMatchers.any());
    org.mockito.Mockito.verifyNoInteractions(audit);
    org.assertj.core.api.Assertions.assertThat(order.portion(PORTION_B).isPending()).isTrue();
  }
}
```

Use a real generated mapper in mapping tests. With a Spring mapper, instantiate its generated implementation and explicit helper mappers for a unit test, or import only those beans in a narrow Spring test. Do not stub the mapper's output. Cases: exact USD amount/typed ID, null optional voucher, missing required field validation, response field allowlist, PATCH absent versus explicit null and unknown enums. A compile-negative fixture that adds an unmapped target field must fail MapStruct processing; it is a separate fixture build, not broken code committed into main sources.

| AT-QUERY-CURSOR | Same timestamps/ranks, foreign owner, modified cursor/filter | Unique ordering; bounded pages; owner/filter rechecked; malformed cursor rejected |
| AT-UC-04-OWN-ORDER-READ | Owned/foreign orders, one and maximum-size pages, concurrent payment or cancellation between projection reads | Full response matches OpenAPI; missing/foreign detail 404; query count does not grow per order or portion; each response represents one committed state |
| AT-QUERY-FTS | Text, blank query, punctuation, inactive Seller, changed title | Parameterized query; current eligibility; generated vector follows update |

Use MVC slices with actual security/advice and controlled application port doubles. A mocked JWT principal tests authority routing, not cryptographic validation; add real-signed-token full-context tests for signature/issuer/audience/expiry. Full transaction tests use `@SpringBootTest` and isolated PostgreSQL. For HTTP tests, the request transaction is separate from the test thread: do not rely on test-level rollback to clean server writes.

Concurrency harness: prepare committed fixtures; use two independent connections/transactions and CountDownLatch/CyclicBarrier; wait with bounded Future timeouts; inspect committed state using a fresh connection. Do not coordinate with arbitrary sleep. Release blocked workers in finally and close executors. Test both legal serial outcomes of cancel/payment; do not assume scheduler order. Audit cleanup uses disposable database lifecycle, not DELETE from append-only audit.

## Architecture scenario catalog

| ID | Rule | Negative fixture that must fail |
| --- | --- | --- |
| ARCH-01 | Domain has no Spring/JDBC/HTTP/JPA/mapper dependency | A root imports JdbcTemplate or a web DTO |
| ARCH-02 | Only module API is consumed across modules; dependency allowlist has no cycles | Review calls Ordering internal repository; Catalog imports Reviews |
| ARCH-03 | Application depends inward and on ports, not adapters | PlaceOrderHandler constructs JdbcOrderAdapter |
| ARCH-04 | Web facade/controller uses input-port views, not domain or output-port types | Controller saves CustomerOrder, injects JdbcTemplate, or maps a repository-port nested DTO |
| ARCH-05 | Query handlers use read ports; write handlers use command contracts | Query handler injects a command repository |
| ARCH-06 | JDBC implementation stays in outbound adapter; no independent SellerOrder write repository | A handler issues SQL or a portion repository bypasses root lock |
| ARCH-07 | Mapper and generated implementation stay in the owner adapter; no root MappingTarget | A mapper lives in domain; source mapper declares aggregate mutation |
| ARCH-08 | All expected modules participate in explicit Modulith discovery | Remove a module annotation and observe module inventory failure |
| ARCH-09 | Lombok cannot generate constructors | Compile/source fixture uses RequiredArgsConstructor, Data or Builder |
| ARCH-10 | Test suites actually execute and required slices are nonempty | Rename source root/package so an expected domain or integration suite imports nothing |

## ArchUnit templates

Import only production classes for the application rules, but include generated production mapper implementations. Keep architecture test fixtures outside `com.example.marketplace` so they are not accidentally scanned as application code. ArchUnit inspects compiled dependencies, as described in its [user guide](https://www.archunit.org/userguide/html/000_Index.html).

```java
import com.tngtech.archunit.core.domain.JavaClasses;
import com.tngtech.archunit.core.importer.ClassFileImporter;
import com.tngtech.archunit.core.importer.ImportOption;
import org.junit.jupiter.api.Test;
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.*;
import static com.tngtech.archunit.library.dependencies.SlicesRuleDefinition.slices;
import static org.assertj.core.api.Assertions.assertThat;

class ArchitectureTest {
  static final String BASE = "com.example.marketplace";
  static final JavaClasses CODE = new ClassFileImporter()
      .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
      .importPackages(BASE);

  @Test void productionAndDomainAreActuallyImported() {
    assertThat(CODE).isNotEmpty();
    assertThat(CODE.stream().filter(c -> c.getPackageName().contains(".domain")))
        .isNotEmpty();
  }

  @Test void domainIsIndependent() {
    noClasses().that().resideInAPackage("..domain..")
      .should().dependOnClassesThat().resideInAnyPackage(
          "org.springframework..", "java.sql..", "javax.sql..", "jakarta.persistence..",
          "org.mapstruct..", "..adapter..", "..application..", "..api..")
      .check(CODE);
  }

  @Test void applicationCannotDependOnAdapters() {
    noClasses().that().resideInAPackage("..application..")
      .should().dependOnClassesThat().resideInAnyPackage(
          "..adapter..", "org.springframework.jdbc..", "jakarta.servlet..")
      .check(CODE);
  }

  @Test void webUsesInputContracts() {
    noClasses().that().resideInAPackage("..adapter.in.web..")
      .should().dependOnClassesThat().resideInAnyPackage(
          "..domain..", "..application.port.out..", "..adapter.out..", "org.springframework.jdbc..")
      .check(CODE);
  }

  @Test void queriesCannotUseWritePorts() {
    noClasses().that().resideInAPackage("..application.query..")
      .should().dependOnClassesThat().resideInAnyPackage("..application.port.out.command..")
      .check(CODE);
  }

  @Test void modulesHaveNoCodeCycles() {
    slices().matching(BASE + ".(*)..").should().beFreeOfCycles().check(CODE);
  }

  @Test void mapperImplementationsStayInAdapters() {
    classes().that().haveSimpleNameEndingWith("Mapper")
      .or().haveSimpleNameEndingWith("MapperImpl")
      .should().resideInAPackage("..adapter..").check(CODE);
  }
}
```

These names are project conventions: suffix-based rules must be paired with a source check for `@Mapper` declarations and a module inventory test, not treated as a universal proof. Source-retained annotations may disappear from bytecode. Enforce Lombok restrictions through `lombok.config` plus source/compile-negative fixtures; enforce forbidden root `@MappingTarget` through source/type-aware checks and mapping behavior tests.

```java
@Test void allDeclaredModulesAreVerified() {
  var expected = java.util.Set.of("shared", "identity", "catalog", "inventory", "cart",
      "promotion", "ordering", "review", "discovery", "administration", "notification", "audit");
  for (String name : expected) {
    var info = CODE.get("com.example.marketplace." + name + ".package-info");
    assertThat(info.isAnnotatedWith(org.springframework.modulith.ApplicationModule.class)).isTrue();
  }
  org.springframework.modulith.core.ApplicationModules
      .of(MarketplaceApplication.class).verify();
}
```

Place the second method in the same class (or share CODE explicitly). Each module requires its package-info declaration and dependency allowlist from [section 3.1](../3-technical-decision/3.1-modular-monolith.md). Verification tests must also reject an unexpected application module unless the catalog is deliberately updated. Use the pinned Modulith API to compare detected module names with the expected set; do not silently skip a missing module because its implementation is new.

For each ARCH rule, create a minimal valid fixture and a violating fixture, then assert that rule evaluation accepts the first and reports a violation for the second. Keep fixtures in a separate test source/build and import them explicitly with ClassFileImporter. No blanket `allowEmptyShould(true)`, global rule freeze or ignore-all-generated-code. During bootstrap, add a missing domain/type shell and test the rule before implementing behavior; a temporary scoped exception requires a reason, owner and removal condition.

ArchUnit cannot prove that a query adapter's SQL is read-only, that a lock is held through commit, or that a JWT claim is trusted. Pair ARCH-05/06 with transaction/SQL tests and read-only query connection policy. Dependency bans also need a build dependency inventory check to reject forbidden libraries even when no compiled class uses them yet.

## CI sequence and evidence

```text
scenario readiness + test source + RED evidence
  -> annotation processing / source-policy checks / compile
  -> domain + mapper + application tests (JUnit 5, Mockito, AssertJ)
  -> ArchUnit + Modulith + expected-suite inventory
  -> MVC + security tests
  -> Flyway + PostgreSQL constraints / concurrency / rollback
  -> prod-profile checks and relevant API/UI integration
  -> GREEN evidence, review and refactor rerun
```

Use Gradle `useJUnitPlatform()` and explicit suite dependencies. Preserve test reports and count executed tests by suite; a green compile with zero discovered tests is not a pass. CI validates the current behavior; test-first ordering is evidenced by scenario/test revisions and RED logs, not inferred solely from a final green build. Coordinator checks that evidence before dispatching a feature implementation worker.

The [skills/subagents plan](inkdrop://note/7oHjDcgQ) assigns scenario ownership to spec-architect, automated test authoring/RED verification to verification-engineer and implementation only after that gate to the feature worker. Version/cursor, merge and review edit/removal contracts are approved. Undefined voucher details and initial review visibility must be specified for affected tests; unrelated scenarios continue.
