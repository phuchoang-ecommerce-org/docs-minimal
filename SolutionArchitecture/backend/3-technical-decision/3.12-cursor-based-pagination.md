# Cursor-based Pagination

Use keyset pagination for Member orders (UC-04/05), Seller portions (UC-07), audit (UC-10) and other growing lists. Sort by immutable created_at plus unique ID; neither timestamp alone nor offset provides the required deterministic boundary. PostgreSQL requires a unique ordering for predictable limited subsets. [Query ordering](https://www.postgresql.org/docs/18/queries-limit.html).

```sql
-- First page; bind member_id from the authenticated actor, not the request.
SELECT id, status, total_usd, created_at
FROM marketplace.customer_order
WHERE member_id = :member_id
ORDER BY created_at DESC, id DESC
LIMIT :fetch_limit;

-- Next page; fetch_limit = validated page_size + 1.
SELECT id, status, total_usd, created_at
FROM marketplace.customer_order
WHERE member_id = :member_id
  AND (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT :fetch_limit;
```

The V1 index `(member_id, created_at DESC, id DESC)` supports both paths. Return at most page_size rows, hasNext from the extra row, and nextCursor from the last returned row (not the extra row). The contract page range is 1–100, default 20.

Cursor content: version, exact timestamp precision, UUID, sort choice and filter fingerprint. Encode as Base64URL and authenticate it with a server MAC; reject malformed/version/filter mismatches as 400. Cursor contents never grant access: owner predicates are reapplied on every request. Do not reuse an order cursor for audit or change filters mid-stream. Use Instant/microsecond-compatible parsing, not display-formatted time.

New rows before the cursor do not repeat already seen rows; deletions can reduce page size. This is not a cross-request snapshot. For stable report exports, define an as-of boundary/transaction separately. Seller pages join portions to parent orders, constrain seller_id, and use `(customer_order.created_at, seller_order.id)` as a unique ordering. Do not use mutable payment status as an ordering key; it may be a filter.

[OpenAPI](../../api-contract/openapi.yaml) now defines the cursor envelope for all lists. Products/categories/addresses/Sellers have no created_at in the current DDL, so these lists use immutable ID descending; orders/reviews/audit retain timestamp plus ID. Product search retains ID ordering, not relevance ordering. Tests cover equal timestamps, final/empty page, changed filters, foreign actor and a concurrent insertion.
