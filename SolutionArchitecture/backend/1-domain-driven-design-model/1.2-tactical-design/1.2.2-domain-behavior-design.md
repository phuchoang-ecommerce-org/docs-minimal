## Domain Behavior Specification

Behavior uses the roots and value objects in [Domain Model Design](./1.2.1-domain-model-design.md). Use-case IDs refer to the [BA use-case catalog](../../../../BusinessAnalyst/use-cases.md); existing [integration requirements](../1.1-strategic-design/1.1.3-bounded-context-design.md#preliminary-integration-contract) still apply.

| Use case | Rich-model operation | Domain service / policy | Outcome or rejection |
| --- | --- | --- | --- |
| UC-01 | Read published Product and visible Review summaries | PurchaseEligibilityPolicy for discovery; image fallback is presentation behavior | Exclude inactive/unpublished listings; image failure leaves product usable |
| UC-02 | Cart.setQuantity / removeLine | CartMergePolicy validates and combines intent | Reject invalid quantity and foreign cart; no stock decrement |
| UC-03 | Account creation/identity validation; Cart.mergeFromGuest | Credential verification stays in security boundary; merge consumes Guest source once | Failed credentials do not modify cart; repeat successful merge does not add quantities twice |
| UC-04 | OrderFactory.place; StockItem.decrease; Voucher.validateRedemption | PurchaseEligibilityPolicy; VoucherPolicy; DiscountAllocationPolicy | One order, snapshots and portions or no write; replay original result for same key/payload |
| UC-05 | CustomerOrder.cancel; StockItem.restore | Cancellation policy belongs to order root | Any Paid portion or prior cancellation blocks mutation; restore exactly once |
| UC-06 | Product.changePrice / setPublication / attachImage / removeImage; StockItem.setOnHand | ImageSourcePolicy; Seller ownership checked by owning services/root | No cross-Seller writes; reject unsafe images/negative stock |
| UC-07 | CustomerOrder.recordCod(sellerOrderId, sellerId, time) | No independent payment service owns state | Reject cancelled order, foreign portion and duplicate payment; derive whole-order payment status |
| UC-08 | Review.create / edit / delete | ReviewEligibilityPolicy consumes Ordering evidence | Require paid purchase, own review and valid rating; duplicate creation fails |
| UC-09 | SellerShop.changeStatus; Category update; Product moderation | Admin role/reason supplied after authorization | Governed changes audited; no mutation through report queries |
| UC-10 | Review.setVisibility | Review moderation policy | Public summary follows visibility; reports stay bounded and read-only |

Root methods preserve their invariants even if invoked without HTTP controllers. Actor authentication, transaction opening and DTO mapping remain application responsibilities. A domain policy receives facts/values; it does not parse JWTs, make HTTP calls or commit SQL. A domain service is justified only when behavior spans roots and has no natural root owner: CartMergePolicy and DiscountAllocationPolicy are examples. CustomerOrder cancellation and COD status stay on CustomerOrder.

### Checkout and concurrent mutations

```text
checkout(actor, intent, key):                       // UC-04
  in transaction:
    replay = orders.findByMemberKey(actor.id, key)
    if replay: return compareFingerprintOrConflict(replay, intent)
    lock Seller, Product, Variant rows in stable order; re-read eligibility/prices
    lock voucher usage if present; validate eligibility and limit
    decrease stock conditionally in stable variant order
    create snapshots, portions, redemption and order; append audit
  on duplicate Member/key: rollback fully, then read committed winner and compare
  on deadlock/version conflict: bounded whole-command retry with fresh reads

cancelOrRecordCod(actor, command):                 // UC-05, UC-07
  in transaction:
    lock customer-order row; reload portions; verify owner
    apply root transition
    if cancel: restore stock once in stable variant order
    persist root and audit
// Seller stock/price/status writers use the same respective rows and locks.
```

Proposed replay semantics compare the submitted body against the stored Member/key intent, then return its original lines even if the cart changed. New cart intent needs a new key; reconcile this rule with OpenAPI before implementation. Unknown commits use the same key. Never retry only part of a transaction.

### Unspecified policies

```text
PENDING BA: merge quantity/limits, checkout cart clearing, voucher rounding/quota
            restoration, initial review visibility, edit-after-moderation,
            Admin payment correction, review deletion/resubmission
PROPOSED merge: sum valid matching variants; report rejected lines; no reservation
```

### Domain services and policies

```text
interface Specification<T>:
  isSatisfiedBy(facts: T): Boolean
  and(other): Specification<T>

class PurchaseEligibilityPolicy implements Specification<OfferFacts>:
  isSatisfiedBy(f): return f.productPublished and f.sellerActive

class ReviewEligibilityPolicy:
  requireEligible(member, product, evidence):       // UC-08
    require evidence.memberId == member and evidence.productId == product
    require evidence.hasPaidPortion

class CartMergeService(policy):                    // UC-02/03; proposed merge policy
  merge(guest, memberCart, validatedLines):
    require not guest.mergeConsumed
    policy.apply(memberCart, validatedLines)
    guest.markMergeConsumed(memberCart.id)

eligibility = new PurchaseEligibilityPolicy()
reviewPolicy = new ReviewEligibilityPolicy()
mergeService = new CartMergeService(approvedMergePolicy)
// Services consume facts/roots, never JWTs, HTTP clients or SQL transactions.
```

## Domain Event Catalog

Events below name proposed domain facts for tests and local domain results. They are not integration events, persisted messages, asynchronous handlers or a requirement to introduce event infrastructure. The current [application architecture](../../2-application-architecture/2.2-application-architecture/2.1.2-application-architecture.md) keeps direct synchronous application calls. Stock, payment, voucher and audit effects must complete in the command transaction rather than depend on event delivery.

| Domain fact | Producer / trigger | Minimum immutable payload | Use and trace |
| --- | --- | --- | --- |
| OrderPlaced | CustomerOrder factory completes validated placement | customerOrderId, memberId, sellerOrderIds, totalUsd | Local result/audit mapping; UC-04 |
| SellerPortionPaid | CustomerOrder accepts one portion transition | customerOrderId, sellerOrderId, sellerId, paidAt | Local result/audit mapping; UC-07 |
| CustomerOrderPaid | Same transition makes all portions Paid | customerOrderId, paidAt | Derived fact, emitted once at final transition; UC-07 |
| OrderCancelled | CustomerOrder accepts cancellation | customerOrderId, memberId, cancelledAt | Audit mapping after stock restoration succeeds; UC-05 |
| GuestCartMerged | Cart merge transaction consumes Guest source | sourceCartId, targetCartId, memberId | Replay/merge test evidence; UC-02, UC-03 |
| SellerStatusChanged | SellerShop accepts governed status change | sellerId, oldStatus, newStatus, actorId, reason | Audit mapping; UC-09 |
| ReviewVisibilityChanged | Review accepts visibility change | reviewId, productId, visible, actorId, reason | Audit mapping; public summaries query current rows; UC-10 |

Each materialized fact also carries a generated eventId, occurredAt, aggregateId and correlationId. Exclude passwords, image bytes, address details and full review text. Fact construction inside a transaction is provisional: discard on rollback. Do not publish success outside the transaction before commit. A duplicate checkout replay or rejected transition creates no second domain fact. No consumer may rely on these in-memory facts for guaranteed delivery, notifications or recovery; durable audit is written explicitly in the transaction.

No `PaymentReceived` event asserts bank verification: the domain knows only the Seller's COD declaration. Integration events and any justified delivery guarantees must be designed separately in a future integration extension.

## Repository Contracts

These are proposed semantic signatures, not language-specific interfaces or new endpoints. Every mutation joins its caller's transaction; repositories never independently commit. Domain methods validate in-memory state while constraints/conditional SQL protect concurrent requests. `expectedVersion` is required where optimistic updates are used; a zero-row update is a conflict, not success.

```text
// Every write joins the caller transaction; no repository commits independently.
interface AccountRepository:
  findByNormalizedLogin
  findById
  insert
  save(expectedVersion)
  // Unique login; one operational role; credentials never returned by public query DTOs

interface AddressRepository:
  findOwned(memberId, addressId)
  saveOwned
  // Return only Member-owned records; supply immutable checkout snapshot

interface SellerShopRepository:
  findBySellerId
  lockForEligibility
  saveStatus
  // Governance updates conflict with checkout eligibility reads until transaction completion

interface CategoryRepository:
  find
  save
  // Admin service authorizes writes; product references remain valid

interface ProductRepository:
  findOwned(sellerId, productId)
  lockOffers(sortedVariantIds)
  save(expectedVersion)
  // Owner-scoped mutation; load current publication/price and coordinate Seller activation evidence; never write stock

interface StockRepository:
  decreaseIfAvailable(variantId, quantity)
  restore(variantId, quantity)
  setOwnedQuantity
  // All callers serialize per stock row; nonnegative constraint; restore is callable only through successful cancellation workflow

interface CartRepository:
  findByOwner
  lockPair(sortedCartIds)
  saveWithMergeConsumption
  // Unique line per variant; serialize Guest consumption and Member cart update atomically; concurrent merge cannot duplicate quantity

interface CustomerOrderRepository:
  findOwned
  findByMemberKey
  lockById
  findParentId(sellerOrderId)
  insert
  save
  // Unique Member/key, immutable snapshots; every portion mutation through locked root; no SellerOrderRepository

interface VoucherRepository / redemption ledger:
  lockByCode
  findUsage
  recordRedemption
  // Validate limits under lock; one ledger entry per order/voucher; rollback all consumption with failed checkout

interface ReviewRepository:
  findOwned
  insert
  save(expectedVersion)
  deleteOwned
  // Unique Member/product; concurrent duplicate fails; deletion representation subject to open BA decision

interface AuditAppender:
  append(entry)
  // Same database transaction as audited change; append-only; failure aborts mutation

```

Owner filters do not replace root guards. A Seller query can resolve a parent order internally, but responses contain only owned portions. Missing and foreign records share the existing 404 behavior. Persistence exceptions are translated to stable application errors; raw SQL errors and foreign-resource details are never returned.

Read capabilities may bypass aggregate hydration: published catalog search, visible review summary, paid-purchase existence, Seller-owned portions and Admin bounded reports. They return immutable projections and cannot mutate domain state. Public review count and average use only visible records directly in PostgreSQL; no event-maintained projection is needed.

### Repository acceptance checks

| Check | Required evidence before implementation acceptance |
| --- | --- |
| Rollback | Inject failure after stock/redemption writes and before audit; no order, usage or quantity change survives |
| Concurrency | Last-unit and last-voucher races allow one winner; losing transaction has no partial write |
| Coordination | Concurrent cancel/mark-paid yields one legal outcome; two Sellers paying different portions derive Paid correctly |
| Idempotency | Concurrent identical key creates one order; changed body conflicts; replay after cart change follows the approved fingerprint rule |
| Ownership | Foreign Product, Cart, Address, Order and Review IDs expose no data and perform no mutation |
| Merge | Concurrent login/merge consumes the same Guest cart once and preserves unrelated Member lines |
| Snapshots | Price, product text and address changes do not alter placed order values |
| Review visibility | Moderation immediately changes the subsequent public summary; deleted-review uniqueness follows the resolved policy |

These are validation requirements, not claims that runtime tests have passed. [Application Architecture](../../2-application-architecture/2.2-application-architecture/2.1.2-application-architecture.md) maps these contracts to ports and adapters.

Repository adapters use RowMapper for SQL conversion and optional MapStruct for row-to-projection conversion. Root rehydration, authorization and state transitions stay explicit. Write the scenario and automated test from [section 4](../../4.%20Automated%20Testing/4.%20Automated%20Testing.md) before implementing behavior.
